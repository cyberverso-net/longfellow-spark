# longfellow-spark

A formally verified Ada/SPARK reimplementation of [Longfellow ZK](https://github.com/google/longfellow-zk) (libzk), built progressively: verified field arithmetic first, then a complete verifier consuming upstream-generated circuits as validated data, then the prover, and finally the circuit compiler.

## Status

Phase A complete (2026-10-16, release 0.1.0): a verifier of Longfellow ZK from the proof string to a verdict, on the explicit circuits of the pinned specification, built in five stages. Phase B (release 0.2.0) added the circuit loader and the interop proofs; Phase C (unreleased, 0.3.0) adds the prover, which reproduces the two upstream proofs byte for byte. Every stage has a chapter in `docs/guide/` with its verification condition table and lessons, and the figures below are those of the commit that closed it (the checks are project-wide, since GNATprove proves the whole project in one run).

No check is justified and no `pragma Assume` is used; Platinum is not a goal. The consolidation after Phase A (ADR 0042 to 0045) put the field contracts at the proof-only assertion level, so the harness set runs in seconds, and restored the hosted proof as a required check. Phase B (ADR 0046 to 0048, chapter 6) loads the circuits the upstream compiler produces (LFC2) and accepts the proofs the upstream prover made for them, from their files, on both fields. Phase C (ADR 0049 to 0053, chapter 7) is complete: the prover produces, from the same inputs and the same seeded generator, exactly the bytes the upstream prover shipped, and its proofs under other seeds are accepted by both verifiers. Next: Phase D, the circuit compiler.

Releases: [CHANGELOG.md](CHANGELOG.md) lists each release by stage with its figures; the current release is 0.3.0, tagged `v0.3.0`.

Pinned spec: **IETF draft-google-cfrg-libzk-03 (23 September 2026)**; field definition in Section 2.2.2. Divergences in later draft versions are handled as explicit migrations (ADR 0002).

## Documentation

The repository is didactic: every stage has a chapter under `docs/guide/` (the mathematics, the algorithm, the Ada/SPARK implementation explained for a reader new to SPARK, and an honest account of what is proved, tested and trusted, with the verification condition table and the commands to reproduce it), and every non-trivial decision has a record under `docs/adr/`. Start with [docs/guide/README.md](docs/guide/README.md) and [docs/guide/verification-approach.md](docs/guide/verification-approach.md); the decision index is [docs/adr/README.md](docs/adr/README.md). ## Trust model

Maintained from day one; every entry is one of proved, tested, or trusted (ADR 0003). The reasoning behind the split is in [docs/guide/verification-approach.md](docs/guide/verification-approach.md).

- **Proved (by GNATprove):** absence of runtime errors on all SPARK code for all inputs (Silver, project-wide invariant); functional contracts where declared Gold in package headers (Phase C: the writers of Sections 7.3, 7.4 and 7.5 writing exactly `Proof_Len` bytes with the Ligero part satisfying the reader's rules `Well_Coded` at the reader's offset and the root first; `Round_Evals` equal to the ghost transcription of `eval_round_poly`; `Encode_Row` with its systematic part equal to the row and its parity part equal to `Lagrange.Evaluate`; each tableau row's placement with the other rows untouched, and the witness slots of each unencoded row holding the witnesses, the triples' values or zeros; `Merkle.Open` producing exactly the digests `Merkle.Verify` consumes, in `Verify`'s own model; `Lqc_Triples` equal to the core's layout; the pad layout `Witness_Count = private inputs + Pad_Total`; every prover unit Silver for any circuit, inputs, configuration and byte stream, with the ownership checks on every heap object; the subfield projection and `In_Subfield` Silver. Phase B: `Uleb128.Read` returning the value of the one to four bytes it consumed, `Circuit_Reader.Read` returning, on `Ok`, a circuit that satisfies `Well_Formed` of the core and whose identifier is the stored one, and null otherwise, with the ownership checks of SPARK on every allocation of the loader and of the two verifiers' working sets; stage 5: `Merkle.Build` against the recursive heap, `Merkle.Verify` accepting only with every index below n, no index repeated and the proof consumed exactly, the root being node 1 of the node model; `Ligero_Geometry.Make` against `LigeroGeometry::new` and Section 4.2.1, every row index in range; `Lagrange.Build` and `Evaluate` against the formula of the Lagrange matrix at the queried columns with inverses that multiply back to one; `Ligero_Proof.Read` accepting only columns that obey the rules of Section 7.4; the three tests of `Ligero_Verifier` against the combinations of Sections 4.4 and 4.5 with `axpy`, `vaxpy`, `dot`, `dot1`; the slice frames by recursion; `Verifier_Core` emitting every term below `Witness_Count`; the two verifiers Silver with their status tied to its cause; the structural contracts of the stage at the proof-only level `Proof_Only`, never compiled; stage 4: the frames of `Transcript` and the statement of `Sumcheck_Transcript` on the ghost absorbed-bytes sequence, `Nat` below n, `Choose` distinct and below n, `GF2_128.To_Bytes` and `From_Bytes`, the layout of `Serialise`, proof-only where SPARKlib's vocabulary is involved; stages 1 to 3 (the field contracts at the proof-only level since ADR 0044, never compiled, so what the harnesses check of the fields is their vectors): `GF2_128.Add`, `GF2_128.Xtime`, `GF2_128.Mul` and `GF2_128.Square`, the latter two proved equal to the ghost reference `Mul_Ref`; that `Mul_Ref` matches the pinned spec's convention is a tested property, not a proved one; `P256_Field.Add`, `Sub`, `Neg`, `Mul`, `Square`, `Is_Canonical`, `From_Bytes`, `To_Bytes`, proved against the ghost integer model `To_Int` and the ghost prime `P`, where `P` is defined from the limbs of p and the proofs establish that it equals 2^256 - 2^224 + 2^192 + 2^96 - 1 as a polynomial identity in 2^32; stage 3, per instance of the two fields: the sumcheck vocabulary `Eq`, `Bindeq`, `Bind`, `Lagrange_Basis`, circuit evaluation `Eval_Quad` and `Eval_Circuit` with the Z assertion semantics, `Bind_G`, `Eval_Bound_Quad`, and the `Expression` operations, each proved equal to a ghost reference that transcribes the draft's formula in a fixed order of operations, with the logical equality `Same`; `Symbolic_Round` is that formula by definition; the core `Verifier_Core` is Silver with proved bounds on what it emits and proved pad indices for the quadratic triples. Structural Gold says nothing about the field laws: that `bindeq` agrees with `eq`, that the Lagrange basis interpolates, that the constraints are the upstream verifier's, are tested).
- **Tested (known-answer and interop vectors in `tests/vectors/`):** for Phase C: the two upstream proofs reproduced byte for byte by `longfellow_prove` from `sha256_inputs.json` and `ecdsa2_inputs.json` under `Simple_Rng (12345)` and `Simple_Rng (123456789)` (`scripts/check.sh cli`, the exit criterion of ADR 0049), and the proofs made under another seed and under the system source accepted by `longfellow_verify`; against an independent Python transcription of the reference prover piece by piece (`gen_prover_vectors.py`): every proof of the repository rewritten identical by the writers (`writer.txt`, `writer_kat`), the pads and the padded sumcheck proofs of the small circuits (`sumcheck_prover.txt`), the Merkle roots, the unencoded rows and the batch openings of the commitments (`ligero_commit.txt`), the complete proofs of the small circuits accepted by `Zk_Verifier` and the statuses `input_length`, `not_satisfied`, `not_in_subfield`, `config_invalid` with the refusal of the proofs an unchecked prover makes of false inputs (`zk_prove.txt`, harness `tests/src/prover_kat.adb`); the sixteen masks of the subfield projection derived in `gen_gf2_128_vectors.py` and checked on all 65536 subfield elements (`gf2_128_kat`); the shapes of the whole tableau slot by slot (ADR 0052); a proof file of this project verified by the upstream `ZkVerifier` through `tests/vectors/upstream/verify_proof_file.rs`, run by hand. For Phase B: the LFC2 format against an independent Python reader and writer and against the two upstream circuit files (`circuit_summary.txt`, `circuit_lfc2.txt`, harness `tests/src/circuit_kat.adb`; the generator's `compute_id` must equal the identifier each upstream file stores), the Appendix B.3 circuits written in LFC2 in two encodings and loaded term for term, 28 malformed files refused with their status; the interop proofs: the two proofs the upstream prover made for `sha256` (GF(2^128)) and `ecdsa2` (P-256) accepted end to end from their files by `Zk_Verifier` through the loaded circuits, and refused with `Merkle_Failed` when one byte is altered in the root, the sumcheck part or the Ligero part (`interop.txt`, harness `cli/src/interop_kat.adb` in the release build, ADR 0048); for stage 5: the Merkle tree against Appendix B.1.1 and an independent reference with openings of every subset of trees up to nine leaves and eight negatives (`merkle.txt`); the geometry and the Lagrange tables against an independent reference with the interpolation property checked by Vandermonde (`ligero_geometry.txt`, `lagrange_*.txt`); the reader of Section 7.4 on subfield runs and every rule violated (`ligero_proof.txt`; harness `tests/src/ligero_kat.adb`); the Ligero verifier step by step against the recorded upstream runs on the two Appendix B.3 proofs, every challenge, chosen column and both sides of each test (`tests/vectors/upstream/ligero_*.txt`, produced by `record_ligero_verifier.rs`), the nonces against Appendix B.3.1, the two complete proofs accepted from the proof string by `Zk_Verifier` and the negative cases of ADR 0040 refused with their status, in `sumcheck_kat`, on both fields (generators `gen_ligero_vectors.py`, `gen_transcript_vectors.py`). For earlier stages: that `GF2_128.Mul_Ref`, hence `Mul`, matches the pinned spec's convention (bit i of the element is the coefficient of x^i, reduction by Q(x)): `tests/vectors/gf2_128_mul.txt` and `gf2_128_square.txt`, checked by the harness `tests/src/gf2_128_kat.adb`. That `GF2_128.Inv` computes the multiplicative inverse (`Inv (x) = x^-1`, `Inv (beta_i) = g^(65535 - i)`, `E * Inv (E) = 1` on random elements, `Inv (Zero) = Zero`): `gf2_128_inv.txt`, every expected value computed by two independent Python references (Fermat exponentiation and extended Euclid on GF(2)[x]) that must agree, and the harness re-checks `E * Inv (E) = One` at run time. For P-256: that the limbs of `P_Limbs` are the prime of Table 1 and that the encoding is the one of Section 7.2.1 (`p256_add.txt`, `p256_mul.txt`, `p256_bytes.txt`, anchored on b, Gx, Gy of RFC 5903 Section 3.1 through the curve equation Gy^2 = Gx^3 - 3 Gx + b); that `P256_Field.Inv` is the inverse (`p256_inv.txt`, Fermat and extended Euclid references agreeing, `E * Inv (E) = One` re-checked at run time); the Solinas reduction table and the inversion chain are additionally verified by the generator `gen_p256_vectors.py`. The file carries three tiers: anchors recomputed and verified against the subfield basis constants of the upstream reference implementation (google/longfellow-zk, commit d5e6be7, `docs/specs/rust/src/algebra/gf2_128.rs` and `lib/gf2k/gf2_128_test.cc`), structural cases from the field definition, and seeded random cases from an independent Python reference (`tests/vectors/gen_gf2_128_vectors.py`, schoolbook product then long division, a different structure from `Mul_Ref`). For stage 4: SHA-256 and AES-256 against FIPS 180-4, CAVP, FIPS 197 and SP 800-38A (`sha256.txt`, `aes256.txt`); the transcript against draft Appendix B.2 byte for byte (`transcript_fs.txt`, 78 chained steps, harness `tests/src/transcript_kat.adb`); the GF(2^128) encoding against Appendix B.3.3 (`gf2_128_bytes.txt`); the challenge derivation end to end, `Replay_Challenges` and the proof reader against the recorded upstream runs on the two Appendix B.3 proofs (`zk_proof_p256_b3_2.txt`, `zk_proof_gf2_128_b3_3.txt`, in `sumcheck_kat`, both ways, injected and replayed); every value recomputed by the generator `gen_transcript_vectors.py`, an independent transcript that aborts on any mismatch (ADR 0032).
- **Trusted (declared, to be reduced over time):** the operating system's random generator (`/dev/urandom`, read outside SPARK by `Os_Random`) for the zero-knowledge property of the proofs `longfellow_prove` makes without `--seed`, and the zero-knowledge and completeness theorems of the padded sumcheck and of Ligero (ADR 0050, ADR 0052; a proof made with `--seed` is predictable by design); that `Simple_Rng` is the generator of the upstream reference test (transcribed, confirmed by the byte identity); the GNAT compiler and GNATprove toolchain, including GNATprove's model of `Ada.Numerics.Big_Numbers.Big_Integers` used by the P-256 ghost model; the SMT solvers (CVC5, Z3, alt-ergo); Fermat's little theorem for both `Inv` behind the test anchors only (on the verification path every inverse is checked at run time by `Checked_Inv`, ADR 0037); the fixed statement hash `DEFAULT_STATEMENT_HASH` of the reference (ADR 0035); that the recordings of the upstream Ligero verifier are faithful to d5e6be7 (ADR 0040); the available memory for one circuit and the two working sets of a verification, allocated on the heap (ADR 0047: a failed allocation is `Storage_Error`, outside the proofs), and GNAT's in-place construction of an aggregate allocator, observed in the spike of ADR 0047 and not a language guarantee; the stage 3 input constraint, still on the stack at about 120 bytes per private input on P-256; the soundness and zero-knowledge theorems of Ligero and of the composition (ADR 0035); the 64-bit target assumption behind `Unsigned_128` (ADR 0012); upstream-generated circuit files as to what they compute (until Phase D; since Phase B their shape is proved `Well_Formed` on load and their identifier recomputed and checked, ADR 0046), and the upstream production reader at d5e6be7 as the definition of the LFC2 format; that `Sha256` and `Aes256` compute SHA-256 and AES-256 beyond the NIST and Appendix B.2 vectors (Silver, ADR 0029); termination of `Transcript.Nat` and of the P-256 sampler, and of their callers in the P-256 instance, a probabilistic property declared with `Always_Terminates` (ADR 0030); SPARKlib's functional sequences as a ghost model (ADR 0031); the completeness of the absorption beyond the two Appendix B.3 proofs, the sequence of calls in `Replay_Challenges` being the checklist; the pinned specification itself; that `Same`, the logical equality of each field wrapper (`Field_GF2_128`, `Field_P256`), is the equality of its element type (its body is the predefined `=` outside SPARK, assumed by the provers, ADR 0023).
- **Out of scope for proofs, compensated:** protocol-level soundness and zero-knowledge (fidelity to spec, cited per step); Fiat-Shamir transcript completeness (the absorption order of `Replay_Challenges`, compared with the reference by reading, tested on the Appendix B.3 proofs; on the prover's side, the byte identity with the upstream proofs tests every draw and absorption); constant-time execution (coding discipline, documented per package; the guarantee is scoped to builds with assertions disabled, because enabled contracts and ghost code execute secret-dependent branches at run time, see the gf2_128.ads header and ADR 0006; declared not applicable to `Transcript`, `Sha256` and `Aes256`, which process the public content of a proof string, ADR 0029, and to every unit of stage 5 for the same reason, ADR 0037; in the prover, constant time by construction unit by unit, the run-length structure of Section 7.4 decided by position and the subfield projection a fixed linear map, two declared branches on witness-derived values, ADR 0051).

Platinum (full functional correctness of the whole system) is explicitly not a goal.

## Building and proving

Requires [Alire](https://alire.ada.dev) with a GNAT toolchain selected (`alr toolchain --select`).

```bash
alr build
alr exec -- gnatprove -P longfellow_spark.gpr
```

Naming: the repository is `longfellow-spark`; the Alire crate and the GPR project are `longfellow_spark`, because Alire crate names and Ada project identifiers do not allow hyphens.

The prover configuration is in `package Prove` of `longfellow_spark.gpr` (ADR 0020): the three provers of level 2 (CVC5, Z3, Alt-Ergo) with a step budget of 600000, so that a proof that fits the budget on one machine fits it on every machine with the same toolchain, and a timeout of 120 seconds as a guard against prover runs that do not terminate; the longest successful proof takes 4 to 10 seconds, so the timeout is never the binding limit. Any change to that configuration is recorded with its rationale (ADR 0003, ADR 0020).

## Testing

The test harness lives under `tests/` and is test code outside the proof perimeter (`SPARK_Mode (Off)`). Its project file compiles the library sources directly with `-gnata`, so every executable contract, loop invariant and ghost function runs: a contract violation surfaces as a test failure. The functional contracts and the ghost models of the two field packages are the exception (ADR 0044): they sit at the proof-only assertion level, proved for all inputs by GNATprove and never compiled, so that the harnesses run in seconds; the fields are tested by their known-answer vectors. This is therefore not the constant-time build (see the trust model above and the `gf2_128.ads` header); never measure or deploy binaries built from `tests/`.

```bash
alr exec -- gprbuild -P tests/longfellow_spark_tests.gpr -p
tests/bin/gf2_128_kat        # default: the gf2_128_*.txt files under tests/vectors/
tests/bin/p256_kat           # default: the p256_*.txt files
tests/bin/sumcheck_kat       # default: sumcheck_*.txt, zk_proof_*.txt, then tests/vectors/upstream/sumcheck_core_*.txt,
                             # with the Ligero verifier and the complete verifier on each recorded circuit, negatives
                             # included, on both fields (seconds, ADR 0044)
tests/bin/transcript_kat     # default: sha256.txt, aes256.txt and transcript_fs.txt (Appendix B.2)
tests/bin/ligero_kat         # default: merkle.txt, ligero_geometry.txt, lagrange_*.txt, ligero_proof.txt
tests/bin/circuit_kat        # default: circuit_summary.txt (the upstream circuit files), circuit_lfc2.txt,
                             # mdoc_summary.txt (the four mDoc production circuits, Phase D)
tests/bin/writer_kat         # default: writer.txt (every proof of the repository rewritten by the writers)
tests/bin/prover_kat         # default: sumcheck_prover.txt, ligero_commit.txt, zk_prove.txt (the prover, piece by piece
                             # and whole, against the Python reference and Zk_Verifier; the upstream Merkle roots)
```

The release project `cli/` compiles the library without assertions and with optimisation, as the verifier and the prover are meant to run; it holds the command-line verifier, the command-line prover and the interop harness, which verifies the two upstream proofs end to end (`tests/vectors/interop.txt`, seconds) and refuses the altered copies with the statuses recorded there; the `cli` step also reproduces the two upstream proofs with the prover (see "Proving" below):

```bash
alr exec -- gprbuild -P cli/longfellow_verify.gpr -p
cli/bin/interop_kat
```

Each harness takes vector file paths as arguments, prints pass and fail counts and exits with a non-zero status on any failure or if no case ran. Vector files are rebuilt with `python3 -I tests/vectors/gen_gf2_128_vectors.py`, `python3 -I tests/vectors/gen_p256_vectors.py`, `python3 -I tests/vectors/gen_sumcheck_vectors.py`, `python3 -I tests/vectors/gen_transcript_vectors.py`, `python3 -I tests/vectors/gen_ligero_vectors.py`, `python3 -I tests/vectors/gen_circuit_vectors.py`, `python3 -I tests/vectors/gen_prover_vectors.py` and `python3 -I tests/vectors/gen_mdoc_vectors.py`; the generators abort if their recomputed anchors disagree with the external constants they embed, and the P-256 generator also re-derives the Solinas reduction table and the inversion chain used by the implementation.

Definition of done, for every commit: `make check` passes. It runs, in order, `alr build`, the check that the proof partitions cover the project, the full proof from a clean session with the project's prover configuration and unproved checks treated as errors, the eight harnesses, the release build with the interop harness, the command-line verifier on the two upstream proofs and the command-line prover reproducing them byte for byte (`make cli`), the vector generators with a comparison against the committed files, and a lint over tracked files; `scripts/check.sh` is the single definition of these steps and `make build`, `make prove`, `make test`, `make cli`, `make vectors` and `make lint` run them one at a time. The harnesses have no slow set: since ADR 0044 they run every case of both fields in seconds, `prover_kat` in about half a minute. There is no pre-push hook: the proof that gates a change is the one the developer runs by hand before the commit (ADR 0041).

## Continuous integration

[![verify](https://github.com/cyberverso-net/longfellow-spark/actions/workflows/verify.yml/badge.svg)](https://github.com/cyberverso-net/longfellow-spark/actions/workflows/verify.yml)
[![prove](https://github.com/cyberverso-net/longfellow-spark/actions/workflows/prove.yml/badge.svg)](https://github.com/cyberverso-net/longfellow-spark/actions/workflows/prove.yml)

Two workflows, both with the same Alire-provisioned toolchain as the local environment (`gnat_native 16.1.0`, `gprbuild 26.0.1`, `gnatprove 16.1.0`, pinned in `alire.toml` and in the workflows' toolchain string), all running the steps of `scripts/check.sh` one at a time (ADR 0018, 0019, 0021, 0034, 0041, 0044, 0045):

- `verify` runs on every push and pull request, on Ubuntu: build, the check that the proof partitions cover the project, the eight harnesses concurrently (ADR 0034; every case of both fields, in seconds since ADR 0044), the release build with the interop harness, the command-line verifier on the two upstream proofs and the command-line prover reproducing them, the vector generators compared with the committed files, and the lint. Required for merging; limit 30 minutes.
- `prove` runs the full proof with the project's prover configuration (ADR 0020) and unproved checks treated as errors, on Ubuntu, as a matrix of eight partitions (`scripts/prove-partitions.txt`, ADR 0033: `p256`, `primitives`, `sumcheck`, `protocol`, `ligero`, `verifier`, `circuits`, `prover`; branch protection requires one check per partition, `prove (<name>)`, so `prove (prover)` is to be added to the required checks with Phase C), one job and one uploaded GNATprove report each, so that the wall time is that of the heaviest partition, within a job limit of sixty minutes (ADR 0054, raised from forty-five when the `prover` partition exceeded it on the hosted runner); `make partitions-check` guarantees that the partitions cover every non-generic unit exactly once. It runs on every pull request to `main`, weekly as an independent record, and on manual dispatch before a release or after a toolchain change; its eight checks are required for merging, one per partition (ADR 0045, which restores the requirement that ADR 0034 had lifted while a pre-push hook proved every push), and the proof that gates a commit remains the one the developer runs locally with `make check` (ADR 0041). Measured on the hosted runner at the close of stage 4: `p256` 7 minutes, `primitives` 6, `sumcheck` and `protocol` 12, of which five to six are the fixed cost of a job; at the close of stage 5, locally with ten provers, `ligero` (geometry, Lagrange, the proof reader) and `verifier` (the Ligero and complete verifiers) take the times recorded in `docs/guide/05-ligero.md`.

A green `verify` badge certifies what `make build`, `make partitions-check`, `make test`, `make vectors` and `make lint` certify locally, on the pinned toolchain. A green `prove` badge certifies that the full proof held on the pinned toolchain at its last run, as the union of its partitions: every SPARK check proved within the step budget, no justification, no `pragma Assume`. Together they certify what `make check` certifies. None says anything about constant time or about specification fidelity beyond the vectors (see the trust model).

To reproduce locally: `make check`.

Branch model: work happens on a branch per stage or block; changes reach `main` through a pull request, merged with `verify` and the `prove` checks green (ADR 0045), after `make check` on the branch (ADR 0041, ADR 0044); direct pushes to `main` are not used.

## Verifying a proof

The command-line verifier (`cli/longfellow_verify`, ADR 0046, chapter 6) loads an LFC2 circuit file, verifies a proof file against it under the circuit's identifier, the transcript label and the Ligero configuration, and prints the status: exit status 0 when the proof is accepted, 1 when it is refused or the circuit is not accepted (the status says why), 2 on a usage or file error. Public inputs are given as big-endian hex integers, 32 digits on GF(2^128) and 64 on P-256. The two upstream examples, whose circuits and proofs are under `tests/vectors/upstream/circuits/`:

```bash
alr exec -- gprbuild -P cli/longfellow_verify.gpr -p
cli/bin/longfellow_verify --field gf2_128 \
   --circuit tests/vectors/upstream/circuits/sha256_circuit.lfc2 \
   --proof tests/vectors/upstream/circuits/sha256_proof.bin \
   --label sha256_spec_test --rate-inv 3 --nreq 16 --ncol 256
cli/bin/longfellow_verify --field p256 \
   --circuit tests/vectors/upstream/circuits/ecdsa2_circuit.lfc2 \
   --proof tests/vectors/upstream/circuits/ecdsa2_proof.bin \
   --label ecdsa2_spec_test --rate-inv 4 --nreq 16 --ncol 256
```

Both print `ok`, in about a second each. The circuit files remain a trusted input as to what they compute (ADR 0011): the verifier proves their shape on load and checks their identifier, and refuses, with `bound_exceeded` or `not_well_formed`, circuits outside this project's bounds or not well formed, which the upstream reader would load.

## Proving

The command-line prover (`cli/longfellow_prove`, ADR 0049, ADR 0050, chapter 7) loads an LFC2 circuit file and an inputs file in the format of the upstream test data (a JSON array of decimal strings, every input, the public ones first), proves the circuit under the transcript label and the Ligero configuration, and writes the proof file: exit status 0 when the proof is written, 1 on a prover status (`input_length`, `not_satisfied`, `not_in_subfield`, `config_invalid`, `exhausted`, or a circuit status), 2 on a usage or file error. Randomness comes from the operating system's generator unless `--seed N` is given, which selects the generator of the upstream reference test and makes the proof reproducible, and predictable: a test option. The two upstream proofs, reproduced byte for byte:

```bash
alr exec -- gprbuild -P cli/longfellow_verify.gpr -p
cli/bin/longfellow_prove --field gf2_128 \
   --circuit tests/vectors/upstream/circuits/sha256_circuit.lfc2 \
   --inputs tests/vectors/upstream/circuits/sha256_inputs.json \
   --label sha256_spec_test --rate-inv 3 --nreq 16 --ncol 256 \
   --seed 12345 --out /tmp/sha256_proof.bin
cmp /tmp/sha256_proof.bin tests/vectors/upstream/circuits/sha256_proof.bin
cli/bin/longfellow_prove --field p256 \
   --circuit tests/vectors/upstream/circuits/ecdsa2_circuit.lfc2 \
   --inputs tests/vectors/upstream/circuits/ecdsa2_inputs.json \
   --label ecdsa2_spec_test --rate-inv 4 --nreq 16 --ncol 256 \
   --seed 123456789 --out /tmp/ecdsa2_proof.bin
cmp /tmp/ecdsa2_proof.bin tests/vectors/upstream/circuits/ecdsa2_proof.bin
```

About six seconds each. Without `--seed` the proof differs at every run and `longfellow_verify` accepts it; the trust model lists the system generator as trusted for zero knowledge. A proof of this project can be checked against the upstream verifier with `tests/vectors/upstream/verify_proof_file.rs`, run by hand in the upstream crate as the README there says.
