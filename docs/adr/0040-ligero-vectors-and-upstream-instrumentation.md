# 0040 Ligero vectors and upstream instrumentation

## Status

Accepted (2026-10-15, before block 2 of stage 5)

## Date

2026-10-15

## Context

The Gold of stage 5 is structural ([ADR 0038](0038-gold-perimeter-for-merkle-and-ligero.md)): it proves the shapes and the formulas, not that a verdict is right. The draft gives, in Appendix B.1.1, one Merkle tree of five leaves with its root and two batch proofs, and in Appendix B.3 two complete proofs with their configuration (RATE_INV 4, NREQ 6, NCOL 64), labels, public inputs and the nonces of the opened columns; the upstream verifier at d5e6be7 accepts them (`unit_tests.rs`). As in stages 3 and 4, the intermediate values of the upstream verifier are what localise a divergence, and they are recorded outside this repository from an instrumentation test kept with the recordings ([ADR 0027](0027-sumcheck-vectors-and-upstream-instrumentation.md)).

## Decision

Vectors for stage 5 come in three tiers, in the notation of [ADR 0009](0009-known-answer-vectors.md), plus negative cases.

- **Tier 1, the draft.** Appendix B.1.1: the five leaves, the root, the batch proofs for leaves (0, 1) and (1, 3), as construction and verification cases of the Merkle package. Appendix B.3.2 and B.3.3: the complete proof bytes (the files `zk_proof_*.txt` of stage 4 gain the Ligero part and the configuration), the labels `sgonal_test_vector_p256` and `sgonal_test_vector_gf2_128`, the public inputs of the appendix; the complete verifier must accept both; the nonces listed in B.3.1 must equal the ones the reader finds after the four polynomials.
- **Tier 2, an independent Python reference** (`gen_ligero_vectors.py`, NIST-free): geometries for a range of configurations and sizes with the constraints of 4.2.1 and the row indices of 4.3, checked against `LigeroGeometry::new` transcribed; Lagrange tables on both fields with the interpolation property checked and the queried columns compared with the full matrix; Merkle trees of 1 to 9 leaves with batch openings of every subset size, generated by the opening procedure of 4.1.3 transcribed; a subfield run case for the GF(2^128) reader, which Appendix B.3.3 does not exercise.
- **Tier 3, recordings of the upstream Ligero verifier** on the two B.3 proofs: u_ldt, alphal, alphaq, u_quad, the chosen column indices, yc and yp of the LDT, linear and quadratic tests, want_dot and proof_dot, produced outside this repository by the author from an instrumentation test added beside `record_sumcheck_core.rs` under `tests/vectors/upstream/`, in the format below. The harness reads them when present; none is synthesised here.
- **Negative cases**, each with the status it must produce: one altered opened column element (`Merkle_Failed`), one altered nonce (`Merkle_Failed`), one altered path digest (`Merkle_Failed`), one altered element of each response polynomial (`LDT_Failed`, `Linear_Failed` or `Linear_Sum_Failed`, `Quadratic_Failed`), a path one digest too long and one too short (`Merkle_Failed`), a second zero-length run (`Proof_Encoding`), a zero-length run not first (`Proof_Encoding`), a run beyond the total (`Proof_Encoding`), trailing bytes (`Proof_Encoding`), a public input count off by one (`Public_Input_Length`). Built by the harness from the B.3 bytes.
- The harness `ligero_kat` runs tiers 1 and 2 and the negative cases; `sumcheck_kat` extends its tier 3 block to the Ligero recording and the complete verifier. Both fail on any case and when no case ran; `scripts/check.sh` runs them.

Format of a tier 3 file (`ligero_<field>_<circuit>.txt`), elements in hex as in ADR 0027, indices in decimal, one line per item in the order the verifier produces them:

```
field <gf2_128|p256>
ligero <circuit> <rate_inv> <nreq> <ncol>
geometry <block> <dblock> <wr> <nw> <nq> <nwrow> <nqt> <nrow>
u_ldt <nqw values>
alphal <nl + 1 values>
alphaq <q> <three values>                 one line per quadratic triple q
u_quad <nqt values>
idx <nreq indices>
ldt <nreq yc values> <nreq yp values>
dot <nreq yc values> <nreq yp values>
dot_sum <want_dot> <proof_dot>
quad <nreq yc values> <nreq yp values>
verdict ok
end
```

## Alternatives considered

- **Tier 1 and the end-to-end verdict only.** Rejected: a wrong index in one test fails the verdict without saying which test, and a verdict that passes by coincidence on two proofs says little; the recordings localise.
- **Generating Ligero proofs in Python** for more circuits. Rejected for this stage: it is the prover, phase C; the two B.3 proofs and the negative cases built from them cover the verifier's paths.
- **Recording the tableau or the Lagrange matrix from upstream.** Not needed: the tables are checked by the tier 2 reference and the queried values by yp of each test.

## Consequences

- `tests/vectors/` gains `merkle.txt`, `ligero_geometry.txt`, `lagrange_*.txt`, the extended `zk_proof_*.txt`, the generator `gen_ligero_vectors.py` and the harness `ligero_kat`; `tests/vectors/upstream/` gains the instrumentation test and two recordings.
- The README trust model moves "the Ligero verifier agrees with the upstream verifier" to tested, with the files named.

## Verification impact

- Provable: nothing; vectors are tests.
- Tested: Merkle against the draft and an independent reference; the geometry and the tables against an independent reference; the tests against the upstream verifier on the B.3 proofs; the two proofs accepted end to end; every status by a negative case.
- Trusted: that the recordings are faithful to d5e6be7 with the kept test; that the draft's vectors are the protocol's (ADR 0027, ADR 0032).
- Constant time: no effect.
